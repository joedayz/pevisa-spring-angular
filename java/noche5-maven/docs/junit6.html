JUnit 6: teoría, Maven y buenas prácticas

JUnit 6 (liberado el 30 de septiembre de 2025) es la versión que acompaña a Java 25: unifica el número de versión de Platform, Jupiter y Vintage, y exige Java 17 como mínimo. El curso usa junit-jupiter 6.1.3, igual que noche05-maven/solution/pom.xml y el backend de Spring Boot.

Teoría: las tres piezas de JUnit

JUnit PlatformEl motor que descubre y ejecuta pruebas. Maven/IntelliJ hablan con él, no directamente con Jupiter.
JUnit JupiterLa API que se usa a diario: @Test, @BeforeEach, Assertions. Es la única pieza que se declara en el pom.xml del curso.
JUnit VintageUn motor aparte para correr pruebas viejas escritas en JUnit 3/4 sobre la misma Platform.

AnotaciónQué haceEjemplo del curso

Declaración en pom.xml

El curso declara JUnit en dos pasos: primero importa el BOM (Bill of Materials) para fijar una sola versión para toda la familia JUnit, y luego agrega junit-jupiter sin indicar versión explícita (la toma del BOM).

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.junit</groupId>
            <artifactId>junit-bom</artifactId>
            <version>6.1.3</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>org.junit.jupiter</groupId>
        <artifactId>junit-jupiter</artifactId>
        <scope>test</scope>
    </dependency>
</dependencies>
ElementoPara qué sirve
junit-bom en dependencyManagement con scope=importFija una sola versión (6.1.3) para junit-jupiter, junit-platform-* y junit-vintage-*, aunque solo se declare una de ellas
junit-jupiterTrae de un solo golpe junit-jupiter-api (anotaciones, Assertions), junit-jupiter-engine (ejecuta las pruebas) y junit-jupiter-params (pruebas parametrizadas)
scope>test</scopeJUnit solo se empaqueta para compilar y correr pruebas; no viaja dentro del .jar final
maven.compiler.release ≥ 17JUnit 6 exige Java 17 como mínimo; el curso usa 25

Un proyecto Spring Boot como backend/pom.xml no necesita declarar nada de esto a mano: spring-boot-starter-webmvc-test ya trae junit-jupiter transitivamente, con la versión que fija spring-boot-starter-parent.

MétodoQué compruebaEjemplo real
assertEquals(esperado, real)Que dos valores sean igualesassertEquals(12, callao.stockDe("ELE-017"))
assertTrue(cond) / assertFalse(cond)Que una condición booleana se cumpla (o no)assertTrue(callao.stockDe("ELE-017") > 0)
assertNull(valor) / assertNotNull(valor)Que algo sea (o no sea) nullassertNotNull(callao)
assertThrows(Clase.class, ejecutable)Que el código lance una excepción concreta, y la devuelve para seguir revisándolaassertThrows(StockInsuficienteException.class, () -> callao.salida("ELE-017", 20))

assertAll(nombre, ejecutables…)Agrupa varias comprobaciones: si una falla, las demás igual se evalúan y se reportan juntasassertAll("stock", () -> assertEquals(6, stock), () -> assertTrue(stock >= 0))
assertIterableEquals(esperada, real)Que dos colecciones tengan los mismos elementos en el mismo ordenComparar la lista de productos leída del CSV
assertTimeout(duracion, ejecutable)Que el código termine dentro de un tiempo límiteassertTimeout(Duration.ofMillis(100), () -> callao.salida(...))

El caso real del curso: assertThrows devuelve la excepción capturada para seguir comprobando su mensaje, igual que se haría con un catch manual.

@Test
void salidaMayorAlStockFalla() {
    StockInsuficienteException ex =
            assertThrows(StockInsuficienteException.class, () -> callao.salida("ELE-017", 20));
    assertEquals("Stock insuficiente de ELE-017: pide 20, hay 8", ex.getMessage());
}

@Test
void ingresoConCeroFalla() {
    assertThrows(IllegalArgumentException.class, () -> callao.ingresar("ELE-017", 0));
}

Buenas prácticas para JUnit 6

✓ Un @BeforeEach que arma estado fresco

Cada prueba parte de un Inventario nuevo (preparar()), así ninguna prueba depende del orden en que corran las demás.

✗ Reusar un campo mutable entre pruebas sin @BeforeEach

Si una prueba modifica el inventario y la siguiente lo da por "limpio", el resultado depende del orden de ejecución.

✓ Nombres de método que explican el caso

salidaMayorAlStockFalla, ingresoConCeroFalla: se lee el reporte de pruebas sin abrir el código.

✗ Nombres genéricos como test1, testInventario

No dicen qué regla de negocio se está verificando ni qué se espera.

✓ Una idea por prueba

ingresoSumaAlStock solo verifica la suma; salidaRestaDelStock solo la resta. Si una falla, se sabe exactamente qué regla se rompió.

✗ Una prueba gigante que hace ingreso, salida y error de stock

Si falla, hay que leer todo el método para saber en qué línea se rompió.

✓ assertThrows para las reglas de negocio

Documenta que salida(20) con 8 disponibles debe lanzar StockInsuficienteException, no solo que "no explota".

✓ Clases y métodos package-private

class InventarioTest y void ingresoSumaAlStock() no necesitan public: JUnit Platform los descubre igual, y es menos ruido.

Extra para JUnit 6 específicamente: el proyecto debe compilar al menos con maven.compiler.release 17 (el curso usa 25). Si se agrupan pruebas con @Nested, el orden de ejecución ahora es determinista por defecto (antes de JUnit 6 no estaba garantizado). Y si conviven pruebas JUnit 4 antiguas, hace falta agregar junit-vintage-engine aparte: ya no viene incluido por defecto.
