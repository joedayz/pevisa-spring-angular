Jerarquía de excepciones en Java

Todas las excepciones cuelgan de Throwable. De ahí se dividen en dos ramas: Error (fallos graves de la JVM, que no se capturan) y Exception (los problemas que sí maneja nuestro código).

  • Throwable
    • Errorno se captura
      • OutOfMemoryError
      • StackOverflowError
    • Exception
      • IOExceptionchecked
      • SQLExceptionchecked
      • RuntimeExceptionunchecked
        • NullPointerException
        • IndexOutOfBoundsException
        • IllegalArgumentException
        • ArithmeticException
        • StockInsuficienteExceptionejemplo del curso

Las dos familias que importan al programar

Familia¿Obliga try/catch o throws?Dónde aparece en el curso
Checked (Exception menos RuntimeException) Sí, el compilador la exige IOException al leer/escribir archivos en noche04-archivos/solution/Archivos.java
Unchecked (RuntimeException y sus hijas) No, es decisión del programador StockInsuficienteException en noche05-maven/solution/.../StockInsuficienteException.java

Error no entra en ninguna de las dos reglas anteriores: no se declara con throws ni se captura, porque representa algo que la aplicación no puede resolver (memoria agotada, pila desbordada, etc.).

Ejemplo checked: IOException

En Archivos.java leer y escribir el CSV puede fallar por disco o permisos, así que el compilador exige capturar IOException (o declarar throws):

try {
    Files.writeString(csv, contenido);
    for (String linea : Files.readAllLines(csv)) {
        // ...
    }
} catch (IOException ex) {
    System.out.println("No se pudo leer el CSV: " + ex.getMessage());
}

Ejemplo unchecked: excepción propia de negocio

StockInsuficienteException extiende RuntimeException porque es una regla de negocio (no hay suficiente stock), no un error externo como el disco o la red. Por eso el compilador no obliga a capturarla, aunque igual se puede manejar:

try {
    bateria.salida(20);
} catch (StockInsuficienteException ex) {
    System.out.println(ex.getMessage());
} finally {
    System.out.println("Fin de la salida");
}

Regla práctica para crear una excepción nueva

¿El problema viene de algo externo (archivo, red, base de datos) y quien llame al método debe enterarse en tiempo de compilación? → extiende Exception (checked).
¿El problema es una regla de negocio o un error de programación que normalmente no se recupera? → extiende RuntimeException (unchecked), como hace el curso con StockInsuficienteException.
