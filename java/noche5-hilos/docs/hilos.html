Hilos en Java: de Thread a los hilos virtuales

El curso llega a los hilos al final de la noche 5, después de Maven y JUnit. El ejemplo es el mismo negocio: restar stock de ELE-017, pero ahora esa resta ocurre dentro de un hilo aparte, en noche05-hilos/solution/Hilos.java.

¿Qué es un hilo?

Un proceso es un programa corriendo, con su propia memoria. Un hilo (Thread) es una línea de ejecución dentro de ese proceso: varios hilos comparten la misma memoria (variables, objetos), pero cada uno avanza con su propia pila de llamadas. El main de cualquier programa Java ya corre en un hilo, aunque nunca se mencione.

ConcurrenciaVarios hilos avanzan en el mismo periodo de tiempo; el sistema operativo o la JVM los va turnando, aunque haya un solo núcleo de CPU
ParalelismoVarios hilos corren al mismo tiempo, literalmente, cada uno en un núcleo de CPU distinto

Hilos de plataforma vs. hilos virtuales

Hasta hace poco, cada Thread en Java era un hilo de plataforma: la JVM reserva un hilo real del sistema operativo por cada uno, con varios megabytes de pila. Crear miles de ellos agota la memoria. Desde Java 21, los hilos virtuales (Project Loom) resuelven esto: la JVM los gestiona ella misma y puede correr millones, porque son mucho más livianos.

Hilo de plataformaHilo virtual
Quién lo administraEl sistema operativoLa JVM

Spring Boot usa hilos virtuales para atender peticiones HTTP con spring.threads.virtual.enabled=true: cada request espera seguido a la base de datos, así que un hilo virtual por petición es barato y no bloquea un hilo real del sistema operativo.

Ciclo de vida de un hilo

NEWcreado, sin start()
→
RUNNABLEcorriendo o listo para correr
→
BLOCKEDespera un synchronized
WAITINGjoin() sin límite
TIMED_WAITINGsleep(ms)
→
TERMINATEDel método del hilo terminó

Un hilo vuelve de BLOCKED/WAITING/TIMED_WAITING a RUNNABLE cuando se cumple la condición que esperaba (se libera el bloqueo, termina el otro hilo, pasa el tiempo). De TERMINATED no se puede volver a arrancar: un Thread se usa una sola vez.

Crear y arrancar un hilo

El curso usa la API moderna de fábricas (Thread.ofVirtual() / Thread.ofPlatform()), más clara que las formas clásicas de heredar de Thread o implementar Runnable.

// Forma del curso: hilo virtual con nombre
Thread salida = Thread.ofVirtual()
        .name("salida-callao")
        .start(() -> stock.addAndGet(-2));

salida.join();   // esperar a que termine
System.out.println(salida.isVirtual()); // true
// Formas clásicas (menos usadas hoy)
class Salida extends Thread {
    public void run() { stock.addAndGet(-2); }
}

Runnable tarea = () -> stock.addAndGet(-2);
new Thread(tarea).start();

El problema de fondo: datos compartidos

Si dos hilos leen y escriben la misma variable al mismo tiempo, puede ocurrir una condición de carrera (race condition): los dos leen el valor viejo antes de que el otro guarde el nuevo, y una de las dos restas "se pierde". Por eso el curso no usa un int stock normal, sino AtomicInteger: sus operaciones (addAndGet, incrementAndGet, get) son atómicas, es decir, no se pueden interrumpir a la mitad.

AtomicInteger stock = new AtomicInteger(8);
Thread salida = Thread.ofVirtual().name("salida-callao").start(() -> stock.addAndGet(-2));
salida.join();
System.out.println("Stock de ELE-017 en Callao: " + stock.get()); // 6, siempre
HerramientaPara qué sirve
AtomicInteger, AtomicLong, AtomicReference<T>Variables con operaciones atómicas, sin necesidad de bloquear nada
synchronizedMarca un bloque o método para que un solo hilo lo ejecute a la vez; el resto esperan en BLOCKED
ExecutorServiceAdministra un grupo de hilos reutilizables; en vez de crear un Thread por tarea, se le entregan tareas y él decide cómo repartirlas
Executors.newVirtualThreadPerTaskExecutor()Un ExecutorService que crea un hilo virtual nuevo por cada tarea que recibe

Si sobra tiempo, el curso lo extiende con ejemplos-concurrencia: un ExecutorService, synchronized y una carrera real de dos salidas sobre el mismo stock, para ver en vivo qué pasa sin AtomicInteger (ver guia.html, noche 5).

Buenas prácticas

✓ Hilos virtuales para tareas de espera (I/O)

Leer un archivo, llamar a una base de datos o a otra API: el hilo pasa la mayor parte del tiempo esperando, así que un hilo virtual es barato y no desperdicia un hilo real del sistema operativo.

✗ Miles de hilos de plataforma para lo mismo

Cada uno reserva varios MB de pila; mil conexiones concurrentes con hilos de plataforma pueden agotar la memoria antes de agotar el CPU.

✓ Variables compartidas con Atomic* o synchronized

El curso usa AtomicInteger para el stock porque dos hilos podrían tocarlo a la vez.

✗ Un int normal modificado desde varios hilos

stock = stock - 2 no es atómico: leer, restar y guardar son tres pasos, y otro hilo puede meterse en medio.

✓ join() antes de leer el resultado

salida.join() garantiza que la resta ya ocurrió antes de imprimir el stock.

✗ Leer el resultado sin esperar al hilo

Sin join(), main puede imprimir el stock viejo, antes de que el hilo termine de restar.

✓ Un ExecutorService (o try-with-resources) para muchas tareas

Pedirle tareas a un ExecutorService en vez de crear un Thread por cada una.

✗ Thread.stop() o ignorar InterruptedException

stop() está obsoleto y es peligroso (puede dejar datos a medio escribir); una InterruptedException atrapada y descartada esconde que alguien pidió cancelar el hilo.

Ejemplos: de lo simple a un ejemplo robusto

Los seis ejemplos siguen el mismo negocio (stock de ELE-017) y suben en complejidad: primero una sola herramienta a la vez, al final todas combinadas en un simulador de salidas concurrentes.

import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;
import java.util.stream.IntStream;

1 · AtomicInteger solo

Lo más simple: una variable con operaciones atómicas, sin bloqueos explícitos.

AtomicInteger stock = new AtomicInteger(8);

stock.incrementAndGet();     // 9
stock.addAndGet(-3);         // 6
stock.get();                 // 6
stock.compareAndSet(6, 0);   // true: solo cambia si todavía vale 6
stock.compareAndSet(6, 99);  // false: ya no vale 6, no cambia nada

compareAndSet(esperado, nuevo) es la base de casi toda la concurrencia sin bloqueos (lock-free): "cambia el valor solo si nadie lo tocó mientras tanto".

2 · synchronized

Cuando la regla de negocio necesita leer y decidir antes de escribir (no alcanza con una sola operación atómica), synchronized protege el bloque completo: un solo hilo a la vez puede ejecutarlo.

class Almacen {
    private int stock = 8;

    synchronized void salida(int cantidad) {
        if (cantidad > stock) {
            throw new StockInsuficienteException("ELE-017", cantidad, stock);
        }
        stock -= cantidad;
    }

    synchronized int stock() {
        return stock;
    }
}

Las dos operaciones (leer stock y validar, luego restar) ocurren como una sola unidad. Sin synchronized, dos hilos podrían leer 8 a la vez, ambos aprobar una salida de 6, y terminar en -4.

3 · Lock / ReentrantLock

Hace lo mismo que synchronized, pero con más control: se puede intentar el bloqueo sin quedar atascado (tryLock), o con un tiempo límite.

class AlmacenConLock {
    private int stock = 8;
    private final Lock candado = new ReentrantLock();

    void salida(int cantidad) {
        candado.lock();
        try {
            if (cantidad > stock) {
                throw new StockInsuficienteException("ELE-017", cantidad, stock);
            }
            stock -= cantidad;
        } finally {
            candado.unlock(); // siempre en finally, incluso si hay excepción
        }
    }

    boolean intentarSalida(int cantidad) {
        if (!candado.tryLock()) {
            return false; // otro hilo ya tiene el candado; no esperamos
        }
        try {
            if (cantidad > stock) return false;
            stock -= cantidad;
            return true;
        } finally {
            candado.unlock();
        }
    }
}

¿synchronized o Lock? synchronized alcanza para el caso normal, es más corto y el candado se libera solo. Lock se usa cuando hace falta tryLock, un tiempo de espera, o varios candados distintos para distintas partes del estado.

4 · ExecutorService con hilos de plataforma

En vez de crear un Thread por cada tarea, se le entregan tareas a un pool fijo que las reparte entre unos pocos hilos reutilizables. Útil para trabajo que usa CPU (cálculos), no para esperar en red.

List<String> pedidos = List.of("ELE-017", "BOS-100", "NEU-190", "ELE-017");
Almacen callao = new Almacen();

try (ExecutorService pool = Executors.newFixedThreadPool(4)) {
    List<Future<?>> tareas = pedidos.stream()
            .map(codigo -> pool.submit(() -> callao.salida(codigo, 2)))
            .toList();

    for (Future<?> tarea : tareas) {
        tarea.get(); // espera cada una y relanza su excepción, si falló
    }
} // el try-with-resources llama a shutdown() y espera a que terminen

System.out.println("Stock final: " + callao.stock());

Desde Java 19, ExecutorService implementa AutoCloseable: el try-with-resources cierra el pool (shutdown() + espera) automáticamente, sin necesidad de un bloque finally aparte.

5 · Hilos virtuales con ExecutorService

Mismo código que el ejemplo anterior, pero con un ejecutor que crea un hilo virtual por tarea. Conviene cuando hay muchísimas tareas que esperan (red, disco, base de datos), como simular 1000 clientes pidiendo salida de stock a la vez.

try (ExecutorService hilos = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<Boolean>> resultados = IntStream.range(0, 1000)
            .mapToObj(i -> hilos.submit(() -> callao.intentarSalida(1)))
            .toList();

    long exitosas = resultados.stream().filter(f -> {
        try {
            return f.get();
        } catch (Exception ex) {
            return false;
        }
    }).count();

    System.out.println("Salidas aprobadas: " + exitosas);
}

La diferencia con el ejemplo 4 es una sola línea: Executors.newFixedThreadPool(4) → Executors.newVirtualThreadPerTaskExecutor(). El resto del código (submit, Future, try-with-resources) es idéntico.

6 · Ejemplo robusto: simulador de salidas concurrentes

Combina ConcurrentHashMap (un AtomicInteger de stock por código), un bucle compare-and-set para la resta sin bloqueos, un ReentrantLock solo para el kardex (una lista que sí necesita bloqueo), e hilos virtuales para simular 50 salidas a la vez.

class AlmacenConcurrente {
    private final Map<String, AtomicInteger> stock = new ConcurrentHashMap<>();
    private final Lock candadoKardex = new ReentrantLock();
    private final List<String> kardex = new ArrayList<>(); // protegida por candadoKardex

    AlmacenConcurrente(Map<String, Integer> inicial) {
        inicial.forEach((codigo, cantidad) -> stock.put(codigo, new AtomicInteger(cantidad)));
    }

    boolean salida(String codigo, int cantidad) {
        AtomicInteger contador = stock.get(codigo);
        if (contador == null) {
            return false;
        }
        int actual;
        do {
            actual = contador.get();
            if (cantidad > actual) {
                return false; // sin stock suficiente, no se toca nada
            }
        } while (!contador.compareAndSet(actual, actual - cantidad));

        registrar(codigo, cantidad); // este paso sí necesita un candado
        return true;
    }

    private void registrar(String codigo, int cantidad) {
        candadoKardex.lock();
        try {
            kardex.add(codigo + " -" + cantidad);
        } finally {
            candadoKardex.unlock();
        }
    }

    int stockDe(String codigo) {
        return stock.getOrDefault(codigo, new AtomicInteger(0)).get();
    }

    List<String> kardex() {
        candadoKardex.lock();
        try {
            return List.copyOf(kardex);
        } finally {
            candadoKardex.unlock();
        }
    }
}

public class SimuladorAlmacen {
    public static void main(String[] args) throws Exception {
        AlmacenConcurrente callao = new AlmacenConcurrente(Map.of("ELE-017", 100));

        try (ExecutorService hilos = Executors.newVirtualThreadPerTaskExecutor()) {
            List<Future<Boolean>> resultados = new ArrayList<>();
            for (int i = 0; i < 50; i++) {
                resultados.add(hilos.submit(() -> callao.salida("ELE-017", 2)));
            }
            for (Future<Boolean> f : resultados) {
                f.get(); // propaga cualquier excepción ocurrida dentro del hilo
            }
        } // el try-with-resources espera a que las 50 tareas terminen

        System.out.println("Stock final: " + callao.stockDe("ELE-017"));       // siempre 0
        System.out.println("Movimientos en el kardex: " + callao.kardex().size()); // siempre 50
    }
}
PiezaPor qué está ahí
ConcurrentHashMapVarios hilos piden stock.get(codigo) a la vez; un HashMap normal puede corromperse con escrituras concurrentes
Bucle do { } while (!compareAndSet(...))Lee el stock, valida y resta como una sola operación lógica, sin bloquear a los demás hilos; si otro hilo cambió el valor en el medio, reintenta solo
ReentrantLock en el kardexArrayList no es segura entre hilos; aquí sí hace falta un candado real, porque agregar a la lista no tiene una versión atómica como AtomicInteger
Executors.newVirtualThreadPerTaskExecutor()Simula 50 "clientes" concurrentes sin gastar 50 hilos reales del sistema operativo
Future<Boolean> + f.get()Espera cada tarea y relanza cualquier excepción que haya ocurrido dentro de ella; sin esto, un error en un hilo podría pasar desapercibido
try-with-resources sobre el ExecutorServiceGarantiza que main no sigue hasta que las 50 tareas terminaron, sin escribir shutdown() a mano

El resultado es determinista a propósito: 50 salidas de 2 unidades sobre 100 de stock siempre dan 0 y siempre 50 líneas de kardex, sin importar en qué orden corrieron los hilos. Si se cambiara AtomicInteger por un int suelto, o se quitara el ReentrantLock del kardex, ambos números dejarían de ser confiables.
