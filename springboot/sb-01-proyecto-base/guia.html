SB-01 · Proyecto base y arquitectura en capas

PEVISA Repuestos · Spring Boot 3.3 · Java 21 · Sesión 1 de 15

¿Qué construimos hoy?

Arrancamos el backend de PEVISA desde cero. Al final de la sesión tendrán un API REST completamente funcional para el catálogo de repuestos, con la estructura de paquetes que usarán en todas las sesiones siguientes. Cada sesión agrega una capa real encima de lo que hoy construyen.

Dominio: PEVISA es líder en autopartes en Perú, con más de 50 años en el mercado y presencia en 30+ países. Su catálogo maneja divisiones como EMPAQUETADURAS, BOSCH, BATERIAS, DENSO. Ese será nuestro modelo de datos durante todo el curso.

Arquitectura en capas

Spring Boot impone una separación de responsabilidades en 4 capas. Cada una tiene una sola razón para cambiar:

BD / Memoria
CapaResponsabilidadNo debe
@RestController Parsear HTTP, validar entrada, delegar al service, construir respuesta HTTP Contener lógica de negocio ni acceder a datos
@Service Lógica de negocio, orquestar repositorios, lanzar excepciones de dominio Saber nada de HTTP ni de SQL
@Repository Acceso a datos (hoy en memoria, en SB-02 con JPA) Contener reglas de negocio
Model / DTO Representar datos del dominio y contratos de la API Mezclar lógica de negocio con serialización HTTP

¿Por qué interfaz en el Repository?
Hoy la implementación es en memoria. En SB-02 la reemplazamos por JPA. El Service habla con la interfaz, nunca con la implementación concreta — así el cambio en SB-02 no toca una sola línea del Service. Este principio se llama Dependency Inversion (la D de SOLID).

¿Por qué DTOs separados del modelo?

❌ Sin DTOs

// El model expone campos internos
// que el cliente no debería ver:
// id autogenerado, fechas de auditoría,
// relaciones lazy que estallan,
// campos de seguridad como password...
@GetMapping
public Repuesto listar() { ... }

✅ Con DTOs

// Request: solo lo que el cliente envía
// Response: solo lo que el cliente necesita
// + campos calculados (estadoStock)
// + control total del contrato de la API
@GetMapping
public RepuestoResponse listar() { ... }

Manejo de errores con RFC 7807

Usamos ProblemDetail (nativo en Spring 6) en lugar de inventar nuestro propio formato. Es el estándar de la industria para errores de API REST.

404 — No encontrado

{
  "type": "https://pevisa.com.pe/errores/
           repuesto-no-encontrado",
  "title": "Repuesto no encontrado",
  "status": 404,
  "detail": "No se encontró el
             repuesto con id: 99"
}

400 — Validación

{
  "type": "https://pevisa.com.pe/errores/
           validacion",
  "title": "Error de validación",
  "status": 400,
  "detail": "codigo: El código es obligatorio,
             precio: debe ser mayor a cero"
}
Nota sobre AOP:
@RestControllerAdvice usa el mismo mecanismo que AOP (proxies dinámicos) para interceptar excepciones de cualquier controller sin que el controller lo sepa. En SB-10 (Auditoría) haremos AOP explícitamente: crearemos aspectos que interceptan llamadas al Service para registrar quién hizo qué y cuándo, sin modificar ningún método del Service.

Validación con Bean Validation

// En el DTO
@NotBlank(message = "El código es obligatorio")
@Size(max = 50)
private String codigo;

@DecimalMin(value = "0.01", message = "El precio debe ser mayor a cero")
private BigDecimal precio;

// En el Controller: @Valid activa la validación
@PostMapping
@ResponseStatus(HttpStatus.CREATED)
public RepuestoResponse crear(@Valid @RequestBody RepuestoRequest request) {
    return servicio.crear(request);
    // Si falla la validación, Spring lanza MethodArgumentNotValidException
    // que nuestro GlobalExceptionHandler convierte en 400
}

Ejercicio de la sesión

El grupo agrega la división CONTINENTAL al catálogo:
  1. Abrir start/ y completar los TODOs del 1 al 28.
  2. Pre-cargar al menos un repuesto de la división CONTINENTAL en el repositorio.
  3. Verificar con curl o Postman:
    • GET /api/v1/repuestos?division=CONTINENTAL devuelve el repuesto.
    • POST con precio negativo devuelve 400 con detalle de validación.
    • GET /api/v1/repuestos/999 devuelve 404 con ProblemDetail.
  4. Correr los tests: mvn test
