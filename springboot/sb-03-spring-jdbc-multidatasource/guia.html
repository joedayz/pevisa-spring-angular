El problema del segundo datasource

// Con UN datasource, Spring Boot auto-configura todo:
// - DataSource (HikariCP)
// - EntityManagerFactory (JPA)
// - TransactionManager
// - JdbcTemplate / JdbcClient

// Con DOS datasources, Spring Boot se paraliza:
// "No qualifying bean of type 'DataSource' — expected single bean
//  but found 2: principalDataSource, legadoDataSource"

// Solución: tomar el control manualmente en @Configuration

DataSourceConfig — la clase que lo resuelve todo

@Configuration
@EnableTransactionManagement
@EnableJpaRepositories(
    basePackages            = "pe.com.pevisa.repuesto.repository.jpa",
    entityManagerFactoryRef = "principalEntityManagerFactory",
    transactionManagerRef   = "principalTransactionManager"
)
public class DataSourceConfig {

    // ── Datasource principal ──────────────────────────────────────
    @Bean @Primary
    @ConfigurationProperties("spring.datasource.hikari")
    public DataSource principalDataSource(...) { ... }

    @Bean("principalEntityManagerFactory") @Primary
    public LocalContainerEntityManagerFactoryBean principalEntityManagerFactory(...) {
        factory.setPackagesToScan("pe.com.pevisa.repuesto.model");
        // Solo escanea entidades JPA — no Pedido (que no es @Entity)
        ...
    }

    @Bean("principalTransactionManager") @Primary
    public PlatformTransactionManager principalTransactionManager(...) { ... }

    // ── Datasource legado ─────────────────────────────────────────
    @Bean("legadoDataSource")            // SIN @Primary
    public DataSource legadoDataSource(...) { ... }

    @Bean("legadoJdbcClient")
    public JdbcClient legadoJdbcClient(
            @Qualifier("legadoDataSource") DataSource ds) {
        return JdbcClient.create(ds);    // un JdbcClient dedicado al legado
    }
}
¿Por qué @EnableJpaRepositories aquí?
Spring Boot activa JPA automáticamente cuando hay un solo DataSource. Con dos, necesitas decirle explícitamente: "los repositorios en el paquete jpa/ usan este EntityManagerFactory y este TransactionManager". PedidoLegadoRepository está en el paquete jdbc/ — JPA no lo toca.

JdbcClient — la API moderna de JDBC en Spring 6

JdbcTemplate (Spring 1-5)

// Verbose: ResultSet manual
jdbcTemplate.query(
  "SELECT * FROM pedidos WHERE estado = ?",
  new Object[]{"PENDIENTE"},
  (rs, row) -> Pedido.builder()
    .id(rs.getLong("id"))
    .numeroPedido(rs.getString("numero_pedido"))
    .estado(rs.getString("estado"))
    // ... 6 campos más
    .build()
);

JdbcClient (Spring 6)

// Fluido: mapeo automático + named params
jdbc.sql("""
    SELECT * FROM pedidos
    WHERE estado = :estado
    """)
    .param("estado", "PENDIENTE")
    .query(Pedido.class)   // mapeo automático
    .list();

.list()0 o más filasNunca

Procedimiento almacenado

-- La función en Postgres
CREATE OR REPLACE FUNCTION resumen_ventas_repuesto(p_codigo VARCHAR)
RETURNS TABLE (
    codigo_repuesto VARCHAR,
    total_unidades  BIGINT,
    total_ingresos  NUMERIC,
    num_pedidos     BIGINT
) AS $$ ... $$ LANGUAGE plpgsql;

// Llamada desde JdbcClient — igual que cualquier SELECT
public Optional<ResumenVentasResponse> resumenVentas(String codigo) {
    return jdbc.sql("SELECT * FROM resumen_ventas_repuesto(:codigo)")
               .param("codigo", codigo)
               .query(ResumenVentasResponse.class)
               .optional();
}
// JdbcClient mapea cada columna de la función a un campo del DTO.
// No hay ResultSet, no hay PreparedStatement, no hay CallableStatement.
Oracle / SQL Server: Para procedimientos con parámetros OUT (patrón clásico de Oracle) usamos SimpleJdbcCall, que es el complemento de JdbcClient para ese caso. JdbcClient cubre el 90% de los casos con funciones que retornan tablas o cursores.

Separación de modelos por datasource

// Repuesto — entidad JPA, datasource principal
@Entity @Table(name = "repuestos")
public class Repuesto { ... }

// Pedido — POJO, datasource legado, NO es @Entity
@Data @Builder
public class Pedido {
    private String numeroPedido;
    private String codigoRepuesto;
    // JdbcClient lo popula directamente desde el ResultSet
}
Error común: mezclar @Entity con objetos JDBC.
Si anotas Pedido con @Entity, Hibernate intentará crear la tabla pedidos en el datasource principal — y fallará porque ese schema no existe ahí, o peor, creará una tabla vacía que confunde al equipo.

Cuándo usar JPA vs JdbcClient

JPA / HibernateJdbcClient
Mejor paraEntidades con ciclo de vida, relaciones, cachéConsultas complejas, BD legadas, proyecciones, batch
Control SQLGenerado por Hibernate (puede sorprender)Total — el SQL es exactamente lo que escribes
SchemaLo controlas tú (Flyway en SB-04)Ya existe, no lo gestionas
RendimientoPuede tener N+1 y flush inesperadoPredecible — una query, un resultado
Transacciones@Transactional con JpaTransactionManager@Transactional con DataSourceTransactionManager

Qué viene en SB-04

Flyway — migraciones de base de datos. Hoy usamos ddl-auto: create-drop que destruye datos al reiniciar. En SB-04 cambiamos eso por migraciones versionadas: el schema evoluciona de forma controlada, auditada y reversible — igual que el código con Git.
