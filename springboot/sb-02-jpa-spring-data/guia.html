El momento de verdad de SB-01

En SB-01 dijimos: "definimos la interfaz para poder cambiar la implementación sin tocar el Service". Hoy lo comprobamos. InMemoryRepuestoRepository desaparece. RepuestoRepository extiende JpaRepository. El Service no cambió ni una línea en su firma pública. El Controller tampoco.

Qué cambia hoy:
  • Repuesto se anota con @Entity → Hibernate la mapea a la tabla repuestos
  • RepuestoRepository extiende JpaRepository → Spring Data genera toda la implementación
  • InMemoryRepuestoRepository se elimina completamente
  • El Service agrega @Transactional ahora que hay una BD real
  • Tres endpoints nuevos: /paginado, /stock-bajo, /buscar
Qué NO cambia: la firma de los métodos del Service ni del Controller existentes.

¿Por qué ddl-auto: create-drop hoy?
Hibernate crea las tablas al arrancar y las elimina al cerrar. Cómodo para desarrollo — nunca para producción.
En SB-04 (Flyway) cambiamos esto a validate y el esquema lo controla Flyway con migraciones versionadas. Nunca más un create-drop que borra datos en producción por accidente.

SB-02 — entidad JPA nuevo

@Entity
@Table(name = "repuestos")
@Data @Builder
@NoArgsConstructor @AllArgsConstructor
public class Repuesto {

    @Id
    @GeneratedValue(strategy = IDENTITY)
    private Long id;

    @Column(nullable=false, unique=true, length=50)
    private String codigo;

    @Column(nullable=false, length=200)
    private String descripcion;

    @Column(nullable=false, length=50)
    private String division;

    @Column(nullable=false, precision=12, scale=2)
    private BigDecimal precio;

    @Column(nullable=false)
    private Integer stock;

    @Column(nullable=false, updatable=false)
    private LocalDateTime createdAt;

    @Column
    private LocalDateTime updatedAt;

    @PrePersist
    void antesDeInsertar() {
        createdAt = updatedAt = LocalDateTime.now();
    }

    @PreUpdate
    void antesDeActualizar() {
        updatedAt = LocalDateTime.now();
    }
}

El repositorio: Spring Data hace el trabajo

public interface RepuestoRepository extends JpaRepository<Repuesto, Long> {

    // ── Consultas derivadas ──────────────────────────────────────────────
    // Spring Data lee el nombre y genera el SQL. No hay implementación.

    Optional<Repuesto> findByCodigo(String codigo);
    // → SELECT * FROM repuestos WHERE codigo = ?

    List<Repuesto> findByDivisionIgnoreCase(String division);
    // → SELECT * FROM repuestos WHERE LOWER(division) = LOWER(?)

    boolean existsByCodigo(String codigo);
    // → SELECT COUNT(*) > 0 FROM repuestos WHERE codigo = ?
    // Más eficiente que findByCodigo: no trae el objeto completo.

    // ── Paginación ───────────────────────────────────────────────────────
    Page<Repuesto> findAll(Pageable pageable);  // heredado de JpaRepository

    // ── JPQL (@Query) ────────────────────────────────────────────────────
    @Query("SELECT r FROM Repuesto r WHERE r.stock < :umbral ORDER BY r.stock ASC")
    List<Repuesto> findRepuestosConStockBajo(@Param("umbral") int umbral);

    @Query("SELECT r FROM Repuesto r WHERE LOWER(r.descripcion) LIKE LOWER(CONCAT('%',:termino,'%'))")
    List<Repuesto> buscarEnDescripcion(@Param("termino") String termino);

    @Query("SELECT SUM(r.precio * r.stock) FROM Repuesto r WHERE r.division = :division")
    BigDecimal calcularValorInventarioPorDivision(@Param("division") String division);
}
JPQL vs SQL nativo: JPQL opera sobre entidades (Repuesto), no sobre tablas. Hibernate lo traduce al dialecto correcto (Postgres, Oracle, H2…). Usa nativeQuery = true solo cuando necesites funciones específicas de la BD (Postgres JSONB, full-text, funciones de ventana, etc.).

@Transactional — ahora sí importa

// A nivel de clase: todas las operaciones son readOnly por defecto.
// Hibernate no rastrea cambios → más rápido y menos memoria.
@Transactional(readOnly = true)
public class RepuestoService {

    // Sobreescribe readOnly para los métodos que escriben en BD.
    // Si lanza RuntimeException → rollback automático. Todo o nada.
    @Transactional
    public RepuestoResponse crear(RepuestoRequest request) { ... }

    @Transactional
    public RepuestoResponse actualizar(Long id, RepuestoRequest request) { ... }

    @Transactional
    public void eliminar(Long id) { ... }
}
Error común: @Transactional en métodos privados no funciona.
Spring crea un proxy alrededor del Service. Las llamadas externas al proxy activan la transacción. Las llamadas internas (this.otroMetodo()) la ignoran.
Regla: @Transactional solo en métodos public llamados desde fuera de la clase.

Paginación

// Service
public PageResponse<RepuestoResponse> listarPaginado(int pagina, int tamano, String ordenarPor) {
    PageRequest pageRequest = PageRequest.of(pagina, tamano, Sort.by(ordenarPor));
    Page<Repuesto> page = repositorio.findAll(pageRequest);

    return PageResponse.<RepuestoResponse>builder()
        .contenido(page.getContent().stream().map(this::toResponse).toList())
        .paginaActual(page.getNumber())
        .totalPaginas(page.getTotalPages())
        .totalElementos(page.getTotalElements())
        .tamanioPagina(page.getSize())
        .ultima(page.isLast())
        .build();
}

// Controller
@GetMapping("/paginado")
public PageResponse<RepuestoResponse> listarPaginado(
        @RequestParam(defaultValue = "0")     int pagina,
        @RequestParam(defaultValue = "10")    int tamano,
        @RequestParam(defaultValue = "codigo") String ordenarPor) {
    return servicio.listarPaginado(pagina, tamano, ordenarPor);
}

El problema N+1 — el más silencioso de los bugs

Escenario: Repuesto tiene una relación @OneToMany List<Imagen> con fetch LAZY.

repositorio.findAll() ejecuta 1 SELECT para traer 100 repuestos.
Luego, cuando el Service accede a repuesto.getImagenes() para cada uno, Hibernate ejecuta 100 SELECTs más → 101 queries totales.

Solución: @Query("SELECT r FROM Repuesto r JOIN FETCH r.imagenes") o @EntityGraph(attributePaths = "imagenes") → 1 sola query con JOIN.

Siempre revisar el log de SQL (show-sql: true) al agregar relaciones.

¿Por qué H2 en tests y no Postgres real?
H2 en modo MODE=PostgreSQL cubre el 95% de los casos sin requerir Docker en cada máquina. El 5% restante (full-text, JSONB, arrays nativos) lo cubriremos en SB-11 con Testcontainers, que levanta un Postgres real en un contenedor Docker durante el test.
