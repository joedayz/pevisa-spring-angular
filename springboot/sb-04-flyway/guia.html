SB-04 · Migraciones de BD con Flyway

PEVISA Repuestos · Spring Boot 3.3 · Java 21 · Sesión 4 de 15

El problema que resuelve Flyway

Desde SB-01 hasta SB-03 usamos ddl-auto: create-drop. Cada reinicio de la app destruye todas las tablas y las vuelve a crear vacías. Eso funciona en un demo de 2 horas. En un proyecto real con un equipo de 5 personas:

Sin Flyway, en un equipo real:
  • Dev A agrega columna marca en su local con un ALTER TABLE a mano
  • Dev B no sabe del cambio — su app explota porque la entidad JPA tiene el campo pero la BD no
  • QA tiene un schema diferente al de producción
  • Nadie sabe qué versión del schema tiene cada entorno
  • En producción alguien corre un script a mano que nadie documentó
Con Flyway: el schema evoluciona igual que el código — con commits, revisiones y un historial auditado. Cada entorno siempre está exactamente en la versión correcta.

El cambio más importante de esta sesión

SB-01 a SB-03

jpa:
  hibernate:
    ddl-auto: create-drop
# Hibernate destruye y recrea

SB-04 en adelante

jpa:
  hibernate:
    ddl-auto: validate
# Hibernate SOLO verifica que

Convención de nombres

src/main/resources/db/migration/
├── V1__crear_tabla_repuestos.sql     ← versión 1
├── V2__datos_iniciales_repuestos.sql ← versión 2
├── V3__agregar_columna_marca.sql     ← versión 3
├── V4__constraint_division_check.sql ← versión 4
└── R__vista_inventario.sql           ← repetible (sin versión)

Patrón: V{version}__{descripcion}.sql
         ↑              ↑↑
         V mayúscula    dos guiones bajos (obligatorio)
PrefijoNombreComportamiento
VVersionadaSe ejecuta una sola vez. Si la modificas después de ejecutarla, Flyway falla por checksum inválido.
UUndo (Pro)Revierte la versión anterior. Solo en Flyway Pro.
RRepetibleSe ejecuta cada vez que cambia su contenido. Ideal para vistas, funciones y procedimientos.

Historial de migraciones de esta sesión

V1
Crear tabla repuestos
Schema base: columnas, constraints UNIQUE y CHECK, índice en división, índice full-text GIN.
V2
Datos iniciales
10 repuestos de ejemplo con divisiones reales de PEVISA. Los datos de referencia también se versionan.
V3
Agregar columna marca + tabla divisiones
ALTER TABLE con datos existentes actualizados. Muestra el flujo correcto de evolución de schema.
V4
Constraint CHECK en división + trigger updated_at
Integridad en BD independiente de la validación Java. Trigger que mantiene updated_at automáticamente.
R__
Vista inventario (repetible)
Vista consolidada con estado de stock calculado. Se recrea automáticamente cuando cambia.

El orden correcto al agregar una columna

-- PASO 1: crear la migración SQL (V3)
ALTER TABLE repuestos ADD COLUMN marca VARCHAR(100);
UPDATE repuestos SET marca = 'Toyota' WHERE codigo = 'EMP-TOYOTA-001';
-- ... resto de UPDATEs
ALTER TABLE repuestos ALTER COLUMN marca SET NOT NULL;

// PASO 2: agregar el campo en la entidad Java
@Column(name = "marca", nullable = false, length = 100)
private String marca;

// PASO 3: actualizar DTOs, Service (toResponse, toModel)

// PASO 4: deploy — Flyway ejecuta V3 → Hibernate valida → pasa ✓
Nunca hagas esto:
Agregar el campo Java antes de crear la migración. Con ddl-auto: validate, Hibernate falla al arrancar porque la columna no existe aún en BD. El orden es siempre: BD primero, Java después.

Flyway en el arranque de Spring Boot

# Orden de inicialización de Spring Boot:
1. Crear DataSource (HikariCP)
2. Flyway.migrate() ← ejecuta migraciones pendientes
3. Hibernate valida schema (ddl-auto: validate)
4. App lista para recibir requests

# Si Flyway falla, la app no arranca — diseño correcto.
# Mejor fallar rápido que correr con un schema desactualizado.

Migraciones en entornos con múltiples instancias

¿Qué pasa si dos instancias arrancan al mismo tiempo y ambas intentan correr V3?

Flyway usa un lock distribuido sobre la tabla flyway_schema_history. La primera instancia obtiene el lock, ejecuta la migración y lo libera. La segunda instancia ve que V3 ya fue aplicada y no hace nada.

Es seguro en Postgres, MySQL y Oracle — todos soportan SELECT FOR UPDATE o LOCK TABLE.

Migraciones repetibles (R__)

-- R__vista_inventario.sql
-- Se recrea CADA VEZ que el archivo cambia (checksum diferente)
CREATE OR REPLACE VIEW vista_inventario AS
SELECT
    r.id, r.codigo, r.descripcion, r.marca, r.division,
    d.nombre        AS nombre_division,
    r.precio, r.stock,
    r.precio * r.stock AS valor_inventario,
    CASE
        WHEN r.stock = 0  THEN 'AGOTADO'
        WHEN r.stock < 10 THEN 'BAJO'
        WHEN r.stock < 50 THEN 'NORMAL'
        ELSE                   'ALTO'
    END             AS estado_stock
FROM repuestos r
LEFT JOIN divisiones d ON d.codigo = r.division;

-- Para modificar la vista: edita el archivo R__ directamente.
-- Flyway detecta el cambio de checksum y la recrea.
-- No necesitas V5, V6, V7... para cada ajuste a la vista.

Ejercicio

  1. Completar los TODOs 1 al 6 en start/.
  2. Levantar Postgres: docker compose up -d
  3. Correr la app y verificar que Flyway ejecuta las 4 migraciones:
    curl http://localhost:8080/actuator/flyway
  4. Verificar la tabla en BD:
    docker exec -it pevisa-postgres psql -U pevisa -d pevisa_db -c "SELECT * FROM flyway_schema_history;"
  5. Consultar la vista:
    docker exec -it pevisa-postgres psql -U pevisa -d pevisa_db -c "SELECT * FROM vista_inventario LIMIT 5;"
  6. Correr tests: mvn test — 21 tests sin Docker.
  7. Desafío: Crear V5__agregar_tabla_categorias.sql con una tabla categorias que agrupe divisiones (ej: MOTOR, ELECTRICO, ACCESORIOS). ¿Qué pasa si intentas modificar V3 en lugar de crear V5?

Qué viene en SB-05

Redis Cache — el catálogo de repuestos de PEVISA tiene miles de productos. Cada GET /api/v1/repuestos golpea Postgres. Con @Cacheable la segunda consulta tarda microsegundos en vez de milisegundos, y la BD respira. Veremos TTL, invalidación y caché distribuida entre instancias.
